# Cloud功能差距分析与 Cloud 追赶计划

> 版本：v1.0  
> 制定日期：2026-09-09  
> 适用项目：`D:\Cloud-Portable\`  
> 参考：Cloud功能、应用场景、营销推广与 G1-G6 管线说明；Cloud 现有 `capability_runtime.py`、`pipeline_orchestrator.py`、`workflow_engine.py`、`digital_employee_factory.py`、`rag_engine.py`、`vector_search.py`、CRM/GEO/内容/Office 等模块。  
> 计划原则：**先补产品内功，再做行业包；先完成结果闭环，再扩充功能目录；每一阶段必须有可运行验收。**

---

## 一、任务目标与边界

### 1.1 总目标

Cloud 不是复制灵策的 110 个数字员工和 117 个技能名称，而是复制并超越其产品机制：

```text
行业问题
  → 数字员工
  → 技能组合
  → 知识检索
  → 工作流编排
  → 交付物
  → 获客/触达/成交
  → 数据回流
  → 经验沉淀
```

### 1.2 产品目标

| 目标 | 交付结果 | 验收标准 |
|---|---|---|
| 能力模型 | 能力目录、数字员工、技能、知识和管线统一注册 | 目录可查询，字段可校验，租户可隔离 |
| 工作执行 | 任务有状态、有子任务、有重试、有 Trace、有异常记录 | 任意任务可定位到输入、阶段、产物和失败原因 |
| 业务闭环 | 内容获客、线索、触达、报价、合同、交付、复盘可串联 | 一个线索能进入 CRM 并形成后续任务 |
| 行业深度 | 装企、医美、泛电商、律所至少有一个真实闭环 | 有输入、产物、指标、案例来源和人工门 |
| 私有化 | 知识、凭证、数据、审计和模型调用不依赖公网黑盒 | 租户数据可迁移，日志可审计，删除有备份 |
| 营销增长 | G1-G6 能从信号跑到反馈，24 账号作为分发拓扑管理 | 内容发布后有曝光、线索、成交、成本归因 |

### 1.3 不纳入本轮追赶的内容

- 不盲目复制 110/117 数量作为营销卖点。
- 不为未使用的股票、玄学、论文、音乐等能力优先开发首页。
- 不自研基础大模型，优先使用 DeepSeek/GLM/Ollama/其他已接入模型。
- 不在没有真实平台账号和授权的情况下伪造“发布成功”。
- 不把医疗、法律、金融的 AI 输出包装成确定性专业结论。

## 二、差距总览

### 2.1 平台能力差距

| 能力 | 灵策机制 | Cloud 现状 | 状态 | 差距/动作 |
|---|---|---|---|---|
| 数字员工 | 岗位 + 技能 + 知识 + 边界 | 已有工厂和模板，已有基础字段 | 部分具备 | 补结构化 mission、知识、工作流、工具、风险和输入输出契约 |
| 技能系统 | SKILL.md + 脚本 + references + assets | 已有加载器、配置、handler、市场 | 基本具备 | 增加能力域/输入输出/风险和版本校验 |
| 知识库 | 企业知识进入数字员工 | 有 RAG/向量检索骨架 | 部分具备 | 补租户、版本、来源、有效期、引用链和高风险复核 |
| 工作流 | 条件、分支、审批、重试、超时、并行 | `workflow_engine.py` 已有完整状态机 | 基本具备 | 把交付物、任务和员工绑定到工作流实例 |
| 统一管线 | 自动/定时/全链/知识/工作流 | `pipeline_orchestrator.py` 已有五类入口 | 已接入内容模式 | 统一 Trace、子任务、事件和失败恢复 |
| 人工确认 | 草稿→确认→生成 | 已有审批和草稿机制 | 基本具备 | 统一 Artifact 契约和 UI/API 确认门 |
| 私有化 | 数据、模型、审计不出公司 | Docker/Nginx/JWT/审计已存在 | 基本具备 | 做租户级密钥、迁移、备份和审计报表 |
| 内容获客 | G1-G6 + 三类直播 + 24 账号 | 内容零件多，闭环已新增 G1-G6 runtime | 部分具备 | 接 CRM、平台适配器、反馈、案例和归因 |
| CRM/线索 | 线索到客户的持续跟进 | CRM、企微、漏斗已有模块 | 部分具备 | 统一 lead/contact/account/opportunity/event 模型 |
| Office 交付 | Word/Excel/PPT/PDF | 已有生成器 | 已具备 | 统一预览、下载、版本、校验和授权 |
| 多租户 | 企业空间、权限、审计 | 已有隔离模块 | 部分具备 | 做全链路租户一致性测试 |
| 平台发布 | 多平台内容适配 | 有发布器和多平台适配器 | 部分具备 | 真实账号授权、发布回执和失败重试 |
| 行业包 | 15 类场景和垂直 SOP | 已有装企、医美等模板 | 部分具备 | 逐行业建立数据、模板、案例、合规和指标 |

## 四、分阶段追赶计划

### 阶段 P0：能力契约与可信执行（第 1—3 天）

**目标：先把“能运行的结果”固定下来，不再用目录数量证明能力。**

执行内容：

1. 落地 A02 数字员工结构化 schema。
2. 落地 A03 技能输入输出契约。
3. 将现有 `capability_runtime.py` 的 Artifact、Trace、G1-G6 接入统一任务表。
4. 统一 `draft → human_approval → generate → verify → deliver`。
5. 增加 `run_id`、租户、来源、风险、校验和字段。
6. 固化 5 个验收用例和 1 条演示流程。

**阶段验收：**

- 任意交付物没有确认不能生成。
- 任一阶段失败能在数据库中找到 Trace。
- G1-G6 顺序可验证。
- 真实发布失败时只返回失败，不伪造成功。

### 阶段 P1：知识、执行、获客、转化（第 4—10 天）

**目标：让数字员工读得到企业知识，并能把结果变成线索和后续任务。**

执行顺序：

```text
B01 知识版本
  → B02 RAG 租户隔离
  → C02 任务状态机
  → C03 员工工作流绑定
  → C05 平台/企微/CRM 适配器
  → D01 获客闭环
  → D02 触达闭环
```

**阶段验收：**

- 回答带来源、版本和有效期。
- 跨租户检索结果为 0。
- 一次内容运行可产生 lead_id。
- 一次跟进任务可关联客户、员工、渠道和内容版本。
- 企微消息有授权、回执和频控。

### 阶段 P2：行业包与交付物闭环（第 11—20 天）

**目标：每个行业包必须能演示“输入—执行—结果—案例”，而不是只有模板。**

优先顺序：

1. 装企：获客 → 报价 → 投标 → 供应商 → 复盘。
2. 泛电商：商品 → 评价 → 客服 → 广告 → 订单。
3. 医美：合规内容 → 咨询 → 线索 → 到店 → 复购。
4. 律所：内容获客 → 咨询 → 合同 → 案件 → 跟进。

**阶段验收：**

- 每个行业包至少一条 E2E 路径。
- 至少一个真实或可核验的量化案例。
- 医疗、法律、财务有专业复核和来源门。
- 报价、合同、投标、方案的审批流可完整跑通。

### 阶段 P3：平台化、可观测和私有化生产化（第 21—35 天）

**目标：从个人开发产物变成可以私有化交付的产品。**

执行内容：

- 多租户、角色、权限、密钥和审计。
- 队列、模型路由、失败重试、checkpoint。
- 平台发布适配器、账号授权和回执。
- 备份、恢复、迁移、脱敏、监控。
- 统一告警：任务失败、模型不可用、队列积压、平台授权失效。
- 首页从“功能数量”改为“今日线索、待跟进、内容 ROI、异常任务”。

**阶段验收：**

- 单租户部署可启动。
- 备份可恢复，租户可迁移。
- 关键操作全审计。
- 任务失败可告警、可定位、可恢复。
- 外部平台无授权时绝不返回“成功”。

### 阶段 P4：规模化经营与案例复制（第 36 天以后）

**目标：用真实结果复制行业，而不是继续堆模块。**

执行内容：

1. 以装企为首个标杆，拿下署名客户。
2. 复用到医美、泛电商、律所。
3. 形成标准培训、入门、案例、数据接入和 CSM 流程。
4. 每月从内容/线索/成交中反哺技能和策略。
5. 形成 1 个可复制的行业 SaaS 交付包。

**阶段验收：**

- 30 天内至少 1 个署名客户。
- 至少 1 个有来源、有口径、有 ROI 的案例。
- 1 个行业包可以脱离创始人手工运行。
- 客户可以查看线索、内容、任务、交付物和结果。
- 新行业包按模板接入，而不是从零开发。

## 五、依赖关系与关键路径

```text
A01 能力目录
 ├── A02 数字员工结构化
 ├── A03 技能契约
 └── A04 行业包规范

A02 + A03 + C02
 └── C03 员工绑定工作流
        ├── D03 交付物
        ├── D01 获客
        └── E01-E04 行业包

B01 知识版本 + B02 租户隔离
 └── D01/D03/E01-E04
        └── G03 客户案例

C05 适配器 + D02 触达
 └── D04 内容反馈
        └── G04 运营看板

F01 租户 + F03 安全 + F05 备份
 └── F04 监控和私有化生产化
```

**关键阻塞点：**

1. 如果不先完成技能契约，员工只能“会聊”不能“交付”。
2. 如果不先完成租户隔离，案例和客户数据不能真正进入 SaaS。
3. 如果不接真实发布和企微适配器，G1-G6 只能停在草稿。
4. 如果没有行业案例，任何 ROI 和效率数字都没有可信来源。
5. 如果没有备份和恢复，私有化交付不能称为生产可用。

## 六、验证矩阵

| 验证项 | 最小输入 | 预期输出 | 失败判定 |
|---|---|---|---|
| 知识问答 | 租户文档 + 问题 | 答案、来源、版本、有效期 | 来源缺失或串租户 |
| 内容管线 | 目标、信号、事实、平台 | G1-G6 trace + 草稿 | 任一阶段不可解释 |
| 人工审批 | 草稿 artifact | approved + final file | 跳过审批生成最终文件 |
| 线索归因 | 内容 run_id + 客户咨询 | lead + source + campaign | 线索没有来源 |
| 触达 | 客户 + 模板 + 授权 | 消息、状态、回执 | 无授权仍标记成功 |
| 报价 | 面积/需求/价格规则 | 报价草稿、审批、Excel/PDF | 税费/数量/版本不透明 |
| 合同 | 合同类型 + 主体 | 合同草稿、审查、Word | 缺主体或授权 |
| 内容反馈 | 曝光、点击、线索、成本 | CTR、CPL、ROI、lesson | 缺数据仍编造结果 |
| 失败恢复 | 中断任务 | checkpoint + 续跑 | 重复写入或状态丢失 |
| 租户隔离 | 两个租户相同关键词 | 各自结果 | 任何跨租户结果 |
| 备份恢复 | 租户完整数据 | 可恢复的租户副本 | 关键表缺失 |

## 七、最终完成定义

Cloud 追平灵策式能力，不以“拥有 110 个数字员工/117 个技能”为完成标准，而以以下 7 个结果为准：

1. 数字员工有岗位使命、边界、知识和可执行技能。
2. 每个技能有输入、输出、来源、风险和验收。
3. 每条管线有完整 Trace、状态、异常和恢复。
4. 内容能进入 CRM、触达客户、记录成交。
5. 交付物有草稿、审批、生成、下载和审计。
6. 行业包有真实模板、真实案例、明确红线。
7. 私有化部署可恢复、可迁移、可审计、可扩展。

完成这 7 项，Cloud 才算真正拥有灵策的产品能力，而不是拥有灵策的功能目录。
