# Cloud能力模型与 Cloud 反哺蓝图

> 版本：v1.0  
> 建模日期：2026-09-09  
> 输入依据：Cloud功能、应用场景、营销推广说明；Cloud 现有 `README.md`、产品开发文档、灵策差距分析、`pipeline_orchestrator.py`、`workflow_engine.py`、`digital_employee_factory.py`、`CLOUDTECH-SKILLS-SPEC.md`、`skills_core/skill_loader.py` 与 `skills/skills.config.json`。  
> 核心方法：**不把 110 个数字员工当成 110 个孤立功能，而是拆成“岗位编排层 + 技能工具层 + 知识数据层 + 执行管线层 + 经营结果层”五层模型。**

---

## 0. 先给结论

灵策真正可复用的不是数字员工数量，而是下面这套产品机制：

```text
行业/岗位问题
    ↓
数字员工（岗位角色、目标、边界、语气）
    ↓
技能组合（输入、步骤、工具、输出）
    ↓
工作流（条件、分支、审批、重试、超时）
    ↓
内容/数据/交付物
    ↓
发布、触达、成交、回流、复盘
    ↓
企业知识与策略资产
```

Cloud 已有 `workflow_engine`、`pipeline_orchestrator`、技能加载器、数字员工工厂、CRM、GEO、内容、Office 生成等底座，**不需要照搬 110/117 个目录项**。正确做法是：把灵策的“能力覆盖”模型化为可配置目录，把 Cloud 已有能力注册进去，把缺失的通用能力补成可插拔技能，把营销 G1-G6 和业务交付物接成可观察管线。

对外仍然只讲三件事：**帮企业赚钱、帮企业省钱、帮企业把工作标准化。** 数字员工和技能数量属于内部能力，不作为客户第一价值表达。

## 1. 五层能力架构

### 1.1 经营结果层：老板要买什么

| 价值结果 | 典型问题 | Cloud 现有承接 | 应新增/强化的统一能力 |
|---|---|---|---|
| 赚钱：获客 | 没有内容、没有线索、投流没回报 | 内容生产、竞品、GEO、CRM、获客专家 | 内容矩阵、线索评分、归因、自动跟进、ROI 归因 |
| 赚钱：转化 | 有流量没客户、有客户不成交 | CRM 漏斗、销售跟进、报价/方案 | 线索→商机→报价→合同→签约的标准化流水线 |
| 省钱：提效 | 文档、分析、测试、重复工作耗时 | Office 生成、数据分析、自动化测试、视频 | 任务队列、批处理、断点续跑、结果验收 |
| 标准化 | 经验在老员工脑中，质量因人而异 | 数字员工工厂、知识库、工作流、RAG | 知识版本、岗位 SOP、模板、行业红线、审批门 |
| AI 升级 | 企业知道要用 AI，但不会用 | AI 店长、技能市场、技能触发 | 意图→数字员工→技能→工作流→交付的自动路由 |

### 1.2 岗位编排层：数字员工模型

数字员工不是一个“聊天机器人名称”，而是一个可执行岗位定义：

```json
{
  "id": "marketing-consultant",
  "name": "营销顾问",
  "industry": "decoration",
  "mission": "把老板的行业问题转成可执行的增长方案",
  "bound_skill_ids": ["competitor-analysis", "geo-strategy", "estimate-budget"],
  "knowledge_base_ids": ["decoration-sales", "local-market"],
  "allowed_workflow_ids": ["lead-diagnosis", "content-campaign"],
  "input_contract": {},
  "output_contract": {},
  "guardrails": [],
  "human_gate": false
}
```

建议统一扩展现有 `digital_employees` 表的字段：

- `mission`：岗位使命和成功标准。
- `bound_skill_ids`：结构化技能绑定，替代只存名称数组。
- `knowledge_scope`：知识库、版本、有效期和权限。
- `allowed_workflows`：该员工可启动的工作流白名单。
- `input_schema/output_schema`：输入输出契约。
- `tools_scope`：允许调用的工具、MCP、浏览器、Office 和平台。
- `risk_level`：低/中/高，决定是否必须人工确认。
- `default_model`、`fallback_models`、`temperature`、`max_tokens`。
- `success_metrics`：该岗位的工作质量指标。
- `version`、`prompt_version`、`created_by`。

### 1.3 技能工具层：最小可复用执行单元

每个技能必须遵循 Cloud 现有 Skills Spec：

1. `SKILL.md`：描述“何时使用、如何做、红线是什么”。
2. `scripts/`：确定性计算、清洗、生成、文件输出。
3. `references/`：行业规则、模板、字段契约、合规知识。
4. `assets/`：表格、图片、模板等资源。
5. 绑定 `skills.config.json` 中的 `handler`，启动时检查 handler 是否存在。
6. 交付物类技能必须经过草稿 → 人工确认 → 生成 → 验收门。
7. 技能结果必须返回：状态、产物、数据来源、置信度、风险、下一步。

技能按能力域统一分类：

| 能力域 | 灵策对应能力 | Cloud 落地策略 |
|---|---|---|
| 办公与文档 | Word、公文、周报、PPT、飞书、腾讯文档 | 现有 Office 技能升级为统一 Artifact Contract |
| 行业专业 | 财报、合同、法律、医疗、学术 | 做成行业包，不塞入通用员工 |
| 生活与健康 | 健身、健康、心理咨询 | 做成可选行业包，合规等级单独定义 |
| 教育 | 志愿、培训、论文 | 做成教育行业包 |
| 数据分析 | BI、图表、财务、股票 | 统一 DataSource→Metric→Insight→Report |
| 内容创作 | 剧本、短剧、分镜、体制写作 | 对接现有内容引擎与品牌声音/反幻觉 |
| 编程与测试 | 单测、API、E2E、TDD | 工具型技能，按权限和隔离环境执行 |
| 知识管理 | FAQ、文档转写、节日/日历 | 对接 RAG、知识库、定时更新 |
| 设计与多媒体 | UI/UX、图片、视频、数字人 | 统一多模态资产和版权/授权元数据 |
| 商业运营 | 预算差异、运营分析 | 做成经营驾驶舱和日报周报 |

### 1.4 知识数据层：让员工真正懂企业

知识不是一次性塞进 Prompt，而是四类对象：

- **企业知识**：制度、产品、价格、案例、话术、合同、FAQ。
- **行业知识**：政策、工艺、材料、市场、法规、竞品。
- **任务知识**：当前客户、线索、项目、报价、合同、交付状态。
- **方法知识**：技能 SOP、工作流、审批规则、内容模板、质量标准。

每条知识必须带：

```text
tenant_id + knowledge_id + source_uri + source_hash
+ version + effective_from/effective_to + access_scope
+ sensitivity + owner + review_status
```

回答问题时，RAG 检索必须返回引用链和来源标记；医疗、法律、财务等高风险领域必须显示“辅助分析/需专业人员复核”。

### 1.5 执行管线层：所有工作最终落到可追踪执行

Cloud 已有五类管线，应继续作为唯一入口：

- `TYPE_AUTOMATIC`：单次内容/业务自动任务。
- `TYPE_SCHEDULED`：定时扫描、生成、检查、发布、回流。
- `TYPE_FULLCHAIN`：高价值任务从输入到多平台产物一次完成。
- `TYPE_KNOWLEDGE`：Inbox → Processed → Pattern → Rule/Skill。
- `TYPE_WORKFLOW`：报价、合同、投标、发布等审批与条件状态机。

每个管线统一携带：

```json
{
  "tenant_id": "...",
  "actor": {"type": "user|system|agent", "id": "..."},
  "goal": "...",
  "digital_employee_id": "...",
  "skill_ids": [],
  "workflow_id": "...",
  "input": {},
  "risk_level": "low|medium|high",
  "run_id": "...",
  "trace_required": true
}
```

## 2. 灵策 15 类场景在 Cloud 的统一模型

下面是“全部纳入模型、按行业包按需启用”，不是把 110 个员工全部复制到首页。

| 场景 | 统一能力模型 | Cloud 当前优势 | 第一优先级 |
|---|---|---|---|
| 平台运营 | 平台账号→内容→发布→互动→复盘 | 多平台发布、竞品、内容分析 | 公众号/小红书/抖音/视频号 |
| 营销 | 目标→人群→渠道→素材→转化 | 营销顾问、报价、GEO、CRM | 律所/电商/装企获客 |
| 内容 | 选题→创作→事实核验→品控→分发 | 8 种内容格式、品牌声音、反幻觉、原创角度 | 内容工厂 |
| 电商 | 商品数据→文案→评价洞察→客服→订单 | 商品/评价/接单可扩展为电商行业包 | 泛电商首批 |
| 跨境 | 平台→翻译→广告→客服→订单/PI | 联网搜索、平台发布、Office 生成 | 跨境客服/广告分析 |
| 财务 | 三表→指标→异常→报告→预警 | 经营分析、预算差异、BI | 装企经营驾驶舱 |
| 法律 | 合同/案件→要素抽取→草稿→审查→审批 | 合同模板、投标方案、审批链 | 律所合同/获客包 |
| 人力 | 员工记录→日报/周报→绩效→知识 | 飞书/文档类可接 | 暂后置 |
| 教育 | 课程/论文/志愿→资料→辅导→交付 | 知识库、内容、Office | 医美/装企后置 |
| 医疗健康 | 健康资料→结构化→辅助判断→转介 | 医美营销/合规包 | 需强合规，不与营销混用 |
| 设计 | 用户→需求→方案→原型→资产 | 图片/视频/数字人/UI | 内容素材生产 |
| 技术 | 需求→代码/测试→报告→CI | 自动化测试、API、E2E | 内部提效，不做对外主卖点 |
| 物流 | SKU/库存→预警→补货→分析 | 数据分析可承载 | 行业包 |
| 玄学 | 输入→规则/模型→结果→提示 | 仅作可选生活包 | 明确非专业医疗/投资建议 |
| 金融/股票 | 数据→指标→报告→风险提示 | 可作为数据工具 | 需要合规和风险分级 |

## 3. 灵策“应用场景”在 Cloud 的业务闭环模型

每个场景不是一段营销文案，而是一个可复制的 `Pain → Trigger → Data → Skill → Workflow → Output → KPI` 对象。

| 场景 | Pain | 触发方式 | 关键数据 | 技能/工作流 | 产物 | KPI |
|---|---|---|---|---|---|---|
| 内容获客 | 不会选题、没有稳定内容 | 定时/老板一句“做本周内容” | 搜索趋势、竞品、历史表现 | G1-G6 + 内容审批 | 选题库、脚本、图文、视频 | 线索、CTR、收藏、有效咨询 |
| 电商转化 | 商品页差、差评没人复盘 | 上架新商品/评价增量 | SKU、评价、广告数据 | 商品优化、评价分析、广告分析 | 标题、详情页、卖点表、预算建议 | CVR、CPC、ACOS、ROAS |
| 广告投放 | 钱烧了不知道效果 | 日报/周报/异常阈值 | 花费、转化、关键词、素材 | 广告分析→预算审批 | 异常报告、调价建议 | ROAS、CPA、增量线索 |
| 平台矩阵 | 多平台重复改写 | 新母内容/定时发布 | 各平台规则、历史表现 | 多平台适配→发布 | 图文、短视频、直播脚本 | 发布成功率、平台互动 |
| 文档提效 | 合同/方案/周报耗时 | 上传文件或 @员工 | 模板、字段、历史版本 | 文档技能→确认门→Office | DOCX/XLSX/PPTX/PDF | 制作时长、返工率 |
| 数据分析 | 数据散、月底才发现问题 | 日/周/月/阈值告警 | 财务、库存、经营数据 | 数据分析→异常→报告 | KPI 仪表盘、预警 | 异常发现时差、决策速度 |
| 技术提效 | 回归慢、发版不稳 | 提交/定时/CI | 代码、测试、覆盖率 | 测试生成→隔离执行→报告 | 测试用例、失败报告 | 缺陷率、回归时长 |
| 知识沉淀 | 老员工离职经验丢失 | 新员工提问/流程变更 | 文档、FAQ、操作记录 | RAG→知识版本→问答 | 回答、引用、更新任务 | 命中率、人工转接率 |
| 行业标准化 | 医生/律师/财务输出不稳定 | 工单/项目节点 | 行业规范、案例、模板 | 岗位员工→技能→审批 | 病历结构化、合同、财报、培训方案 | 首稿通过率、返工率 |

## 4. 营销 G1-G6：模型化为 Cloud 的内容中台

用户给出的 G1-G6 要被改造成“可配置工作流”，而不是一段 SOP 口号。

```text
G1 信号扫描
  输入：行业/城市/平台/时间窗/账号
  输出：趋势事件、用户问题、竞品动作、风险词
  数据源：平台公开趋势、搜索、企业自有数据、新闻/政策
  质量门：来源可追溯、时间有效、敏感内容过滤

G2 选题生成
  输入：G1 信号、品牌定位、目标人群、历史内容
  输出：母题、角度、关键词、预期价值、证据需求
  约束：每题必须回答“赚钱/省钱/提效”至少一问
  质量门：不能只生成空泛 AI 话题

G2.5 原创角度
  输入：候选选题、竞品内容、品牌声音
  输出：冲突点、反常识、第一人称证据、差异化切口
  约束：禁止无来源的“同行都这样做”式编造

G3 内容生产
  输入：母题、平台、格式、字数、素材、授权
  输出：母稿、脚本、分镜、素材清单
  工具：文本/图片/视频/数字人/Office
  质量门：事实引用、版权、AI 味、敏感词

G3.5 事实核查
  输入：草稿、引用、数据、图片/视频元数据
  输出：已证实/待证实/错误、来源、修改建议
  规则：医疗、法律、财务、股票不得自动给出确定性结论

G4 品控
  输入：草稿、平台规范、品牌 SOP、审核规则
  输出：评分、阻断项、修改建议、审批包
  维度：事实、准确、合规、可读、原创、转化、平台适配

G4.5 品牌化
  输入：草稿、brand voice、禁用词、目标客户
  输出：品牌化版本、语言风险、可发布版本
  目标：不是“像 AI”，而是“像企业自己的团队”

G5 分发
  输入：审核通过内容、平台、账号、发布时间
  输出：发布任务、平台版本、失败重试、链接
  规则：高风险内容必须审批；平台规则变更自动暂停

G6 反馈
  输入：曝光、点击、互动、线索、成交、成本
  输出：内容评分、归因结论、下轮策略、待验证实验
  周期：实时/24小时/7天/30天
  目标：反馈必须反哺 G1、G2、G4 和选题库
```

### 内容序列与管线映射

| 内容序列 | 管线阶段 | 关键输出 |
|---|---|---|
| 功能展演 | G2→G3→G4→G5 | Demo 录屏、前后对比、真实步骤 |
| 对比冲击 | G1→G2.5→G3→G4 | 同条件对比、边界说明、证据 |
| 行业痛点 | G1→G2→G3.5→G4 | 痛点拆解、ROI、解决路径 |
| 客户证言 | G3.5→G4→G6 | 授权案例、量化结果、来源 |
| 技术揭秘 | G1→G3.5→G4→G5 | 架构/模型/失败案例/限制 |
| 行业洞察 | G1→G2→G3→G6 | 趋势、预测、证据链 |
| 创始人故事 | G2→G3→G4 | 真实经历、决策、价值观 |

### 24 账号矩阵不应复制成系统账号表

“24 账号”本质是**内容分发拓扑**，不是 24 个数字员工。建议抽象为：

```text
BrandAccount：官方信任/GEO 底盘
PersonaAccount：趋势/产品/市场 3 类 IP
DemoAccount：2 个产品演示账号
VerticalAccount：行业 × 格式 × A/B 测试的账号集合
```

每个账号拥有独立定位、目标、语气、风险等级、发布权限和转化归因，不能用同一个内容复制 24 遍。

## 5. 三种直播的 Cloud 工作流模型

### AI 上班直播

`场景输入 → 任务队列 → AI 执行录屏 → 评论意图分类 → 现场处理 → 风险门 → 结果卡片 → 线索入库 → 次日复盘`

### AI 挑战赛

`固定任务 → 人类基线 → AI执行 → 同口径计时/质量评分 → 结果公开 → 失败案例 → 案例资产 → 内容再生产`

### AI 诊所

`预约/评论 → 企业信息脱敏 → 诊断问卷 → 诊断数字员工 → 现场演示 → 方案草稿 → 人工确认 → 线索/工单 → 7日回访`

直播的核心不是“开着 AI 干活”，而是把每场直播变成：

1. 一个可演示工作流；
2. 一份可复盘实验数据；
3. 一组可发布内容；
4. 5-10 条可追踪线索；
5. 一个进入 CRM 的后续任务。

## 6. 与现有 Cloud 底座的映射

| 灵策抽象能力 | Cloud 现有实现 | 落地动作 |
|---|---|---|
| 数字员工 | `digital_employee_factory.py`、`digital_employees.py` | 增加统一 schema、知识/工作流/权限绑定 |
| 技能市场 | `skill_marketplace.py`、`skills.config.json` | 增加能力域、输入输出契约、风险等级 |

| 人工确认 | `skill_draft.py`、审批引擎 | 所有高风险交付物统一走 `draft → approve → generate → verify` |
| 工作流 | `workflow_engine.py` | 增加节点调用、审计、动态审批链 |
| 管线 | `pipeline_orchestrator.py` | 保持五类入口，增加统一 trace 与子任务模型 |
| 知识库 | `vector_search.py`、RAG | 引入租户、版本、来源、有效期和敏感等级 |
| 内容 | `zhuangqi_content_engine.py`、内容技能 | 接入 G1-G6，补发布回流 |
| 客户 | `crm_integration.py`、线索模块 | 统一 lead/contact/account/opportunity/activity |
| 交付物 | `office_generator.py` | 统一 Artifact Contract 与预览/下载 |
| 触达 | `im_bot.py`、企微技能 | 事件驱动通知、模板、频控、授权记录 |
| 数据分析 | `data_analysis_engine.py`、BI | 统一指标字典、异常检测、报告 |
| 私有化 | 现有 Docker/Nginx/认证 | 所有内容、知识、凭证、审计留在租户域内 |

## 7. 实施优先级：先完整闭环，再扩展数量

### P0：把“数字员工能干活”做成真闭环

1. 扩展数字员工结构：技能、知识、工作流、工具权限、风险等级。
2. 定义统一 `Artifact Contract`：`draft_id / final_uri / source_refs / checksum / preview / risk / status`。
3. 将 Office、报价、合同、投标、发布统一接入确认门。
4. 将 `pipeline_orchestrator` 的五类管线加统一 `trace_id / parent_id / stage_id / retry_id`。
5. 为内容 G1-G6 建工作流模板和可观测指标。

### P1：把“帮老板赚钱/省钱”做深

1. 获客：内容、GEO、线索、CRM、广告分析闭环。
2. 触达：企微/IM 的消息事件、回执、退订、频控。
3. 分析：线索成本、成交率、内容 ROI、广告 ROAS、预算异常。
4. 交付：报价/合同/方案/投标/Office 文件的下载与追踪。
5. 案例：每个行业包必须有真实来源的量化案例，不能只放功能 Demo。

### P2：行业包与账号矩阵

1. 装企：获客→报价→投标→供应商→内容→复盘。
2. 医美：内容合规→咨询→线索→到店→复购，医疗判断必须人工复核。
3. 泛电商：商品→评价→客服→广告→订单。
4. 律所：内容获客→咨询→案件要素→合同/方案→跟进。
5. 24 账号矩阵作为分发拓扑和数据归因，不作为 24 个产品模块。

### P3：长尾能力

- 医疗健康、教育、物流、玄学、金融等行业包。
- 股票、论文、音乐、游戏等不作为首攻产品卖点。
- 这些能力必须按行业包启用，避免把 Cloud 变成目录堆砌。

## 9. 验收标准

Cloud 是否真的拥有灵策式能力，不看“多少个员工”，看以下 7 个验收：

1. **一个员工能否独立完成一个岗位任务**：输入→技能→产物→结果。
2. **一个高风险任务是否必须经过人工确认门**：自然语言确认不能绕过。
3. **一次任务是否全链路可追踪**：知道谁触发、调用什么、读什么、生成什么、哪里失败。
4. **一个内容是否能从信号到反馈闭环**：G1-G6 任何一环都能回溯。
5. **一个客户是否从内容进入 CRM 并进入后续自动化**：曝光→线索→商机→成交。
6. **一份交付物是否有来源、版本、校验和、预览和下载记录**。
7. **一项能力是否可配置、版本化、迁移、启停和审计**：企业能够私有化拥有，而不是只能使用云端黑盒。

## 10. 最终判断

**Cloud 不需要复制灵策的目录数量，而要复制灵策的产品结构。**

- 灵策有“数字员工+技能”两层，Cloud 已有数字员工工厂和技能系统，应继续深化而不是重建。
- 灵策有“获客/省钱/标准化”的业务包装，Cloud 的营销和装企优势正适合作为第一落地样板。
- 灵策的 G1-G6 内容引擎，Cloud 已有内容生产、品牌声音、反幻觉、原创角度、多平台发布、运营看板等零件，缺的是统一编排、数据回流和可量化案例。
- Cloud 应该形成自己的差异化：**不是“功能最多”，而是“行业懂得更深、内容能带来线索、交付物能直接用、数据能证明结果、私有化能真正落地”。**
