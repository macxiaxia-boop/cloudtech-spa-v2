## 1. Why

The V6.2 baseline (524 PASS / 0 FAIL / 7 SKIP) is a *snapshot* — without a
CI gate, the next PR can silently regress the count. T05 closes that gap
by encoding the §1.1 standard verify command as a GitHub Actions workflow
that runs on every PR + push to master.

## 2. Contract

The workflow:

1. Installs `requirements.txt` + `requirements-dev.txt` + `pytest` on a
   clean `ubuntu-latest` runner.
2. Runs the exact command documented in
   `aios_tasks/aios_vnext/INDEX.md` §1.1 (now including
   `tests/test_v63_t03_multitenant_stress.py`).
3. Writes the result to `verify_junit.xml` (xunit2 family).
4. A separate Python step parses the JUnit and **fails the build if
   `failures > 0` or `errors > 0`**. SKIPs are tolerated (they are
   infra-dependent: real Provider API, real SMTP, real PG, ffmpeg binary).
5. Uploads the JUnit artifact for 30 days retention.

This means: any future change that regresses PASS or introduces a FAIL
will block its own PR. The CI is the *enforcement* layer; the test code
is the *observation* layer.

## 3. Triggers

| Trigger | Reason |
|---|---|
| `pull_request` to `master` / `main` | every PR must pass before merge |
| `push` to `master` / `main` | master never regressed |
| `workflow_dispatch` | manual run for ad-hoc verification |

Path filter restricts PR triggers to the test surface
(`tests/**`, `workflows/**`, `billing_real.py`, dependency manifests,
and the workflow itself) so doc-only PRs don't waste CI minutes.

## 4. Why a separate gate step?

The single `pytest` step could fail with non-zero exit on the first
regression, but that mixes "test ran" with "tests passed". A separate
gate step that parses the JUnit XML gives:

- A clear `GATE PASSED` / `GATE FAILED` line in the action log.
- A `$GITHUB_STEP_SUMMARY` table that downstream dashboards can scrape.
- A clean artifact for retrospective analysis (e.g. "did the T03 1000-tenant
  test regress this week?").
